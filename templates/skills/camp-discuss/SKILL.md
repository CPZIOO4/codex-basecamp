# 与用户共同设计

各域主控共用本方法，各自负责本域决定。讨论的深度取决于问题，不要求每次走完固定表单。手机接入、岗位创建、研究调用等后续动作仍以当前授权为准。

## 把问题讨论清楚

- 先用简短自然语言说明你理解的目标、这次要决定的事和已有约束。承接已确认内容，用户只修改其中一项时保留其余决定。
- 先调查自己可以查到的事实：相关结果、代码入口、材料位置或已有规则。只查与当前选择有关的材料，不要求用户替模型查文件，不全库扫描、不自动增加岗位。
- 区分文件或实验直接支持的事实、根据事实作出的推断、尚未采用的建议。主动指出反例和证据不足，不把用户假设或模型猜测直接写成结论。
- 讨论研究时，说明问题为什么值得做、可能机制、什么观察能支持或反驳它，以及结果会改变哪个决定。把输出一致性、参考一致和识别正确性分开；缺真值时说明可研究的行为，避免承诺无法评价的效果。
- 给出推荐方案及理由；有实质取舍才列替代方案。优先问会改变目标、范围、实验解释或不可逆动作的问题，通常每轮聚焦1—3个。用户要求详细讨论时展开相关分支，不为凑问题而追问。
- 有依赖的决策按顺序讨论，尚未回答的前提不能被偷偷当作结论。可独立推进的调查继续做；普通可逆实现细节由主控处理，不转交用户反复确认。
- 遇到容易误解的概念，用具体情景复述其行为。例如实验已执行完但分析仍在进行，按现有 WORKFLOW 判断整个初始目标是否结束。引用现行定义，不在这里再维护一套调度规则。
- 当目标、关键边界和完成标准已足以行动时收敛；不穷举全部设计分支。明确任务直接执行，已授权范围不再次索取批准；仅讨论的请求不自动变成派发实验或新增调用。

## 把共同理解留下来

- 沿用本主控已经绑定的讨论文档，遵循根 README 的讨论记忆规则；有 maintain-project-decisions 时按其生命周期维护。不另建平行 ADR、术语库、任务台账或逐轮纪要。
- 仅在有实质变化时增量保存：目标、已确定的术语、决定与理由、关键证据路径、未解决问题、授权范围和下一步。已否定方案只保留避免重复争论所需的简短原因。
- 用户明确决定、主控推断与待讨论建议分别标清；未回复不视为认可。新决定只覆盖相应旧内容，不把历史事实改成新结论。
- 各业务域决定保存在本域已绑定讨论。共用框架规则的正式落点仍是 WORKFLOW；修改须属于当前授权，避免讨论记录与正式规则相互冲突。
- 结束讨论时用简短总结说明本次确定了什么、还有什么未定、下一步是什么。已授权执行则继续；派发使用 camp-dispatch，让规划场接到清楚问题和必要决定，不复制整段讨论历史。
